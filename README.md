# TraceQ

Traceability-led workspace for pharmaceutical equipment qualification (GMP), with AI as an advisory assistant. The plant, vendors, people, and documents are fictional; all data is synthetic.

Status: the synthetic dataset v0 (the TP-201 package and a held-out TP-202 slice, with answer keys), the eval scorer, and a thin slice of the TraceQ system are in place. The slice turns a corpus into a scored submission, with Haiku baselines for both Equipment (`baselines/`). Slice 1 adds Proposal Decisions: a human accepts, rejects or reclassifies each Proposal of an imported run, stored in Postgres with an append-only Audit Trail. The dataset is frozen at version 0.1.1 (2026-11-17): a practitioner's plausibility check of the TP-201 values and a follow-up form on criticality and transport sensitivity are in; the remaining risk-assessment scores were signed off by the owner and are marked "not reviewed by a practitioner", and TP-202's values are LLM-drafted, so its rates are development signals ([`DATASHEET.md`](DATASHEET.md)).

## Development

```sh
pip install pre-commit
pre-commit install
```

Tests: `uv sync && uv run pytest`. Types: `uv run pyright`.

Render: `uv run python -m traceq_dataset.render world/tp201.yaml [--t0 YYYY-MM-DD] [--seed N] [--out dist]`. Paper documents (`scan:` in world data) are written only as their scan. Output goes to `dist/` (gitignored) with the corpus `manifest.json`; the corpus is published as a Release asset, never committed.

Corpus release: the eval corpus (TP-201 and the held-out TP-202 slice, T0 2026-06-01, seed 0) is published as a GitHub Release asset per dataset version, built in a container with pinned versions (`docker/corpus.Dockerfile`: base image by digest, libraries by `uv.lock`). Release 0.1.1 is **frozen** (what is not reviewed by a practitioner is listed in [`DATASHEET.md`](DATASHEET.md)); both baselines (`baselines/TP-201.json`, `baselines/TP-202.json`) are taken on it. Release 0.1.0 is an earlier pre-release, not frozen. Fetch it with `gh release download corpus-v0.1.1 --repo gedeyandi123/traceq --pattern 'corpus-0.1.1.tar.gz*'`, check it with `sha256sum -c corpus-0.1.1.tar.gz.sha256`, extract it, and pass `t0-2026-06-01/` to `traceq run`; check the files against its `manifest.json` (SHA-256). To rebuild: `docker build -f docker/corpus.Dockerfile -t traceq-corpus .` then `docker run --rm -v "$PWD/out:/out" traceq-corpus`. To pack the folder the build wrote (the folder that contains `t0-2026-06-01/`) into the release asset and its `.sha256`: `uv run python scripts/pack_release.py out corpus-0.1.1.tar.gz` (GNU tar, POSIX-sorted members, fixed time, owner and modes, gzip without name or timestamp; the tar stream is reproducible, the gzip bytes are not across tools). The release bytes are canonical (extraction cache keys use them).

Answer key: `uv run python -m traceq_dataset.answer_key world/tp201.yaml [--check]` derives `answer_key/TP-201/*.yaml` from world data and the eval corpus. Never edit it by hand; regenerate it after changing world data or the renderer (`--check` and the tests fail on a stale key).

Review Package (design §11, spec #196): `TP-201-OQ-draft` 0.1.0, labelled "defect types chosen before the practitioner session; dev only", is a site OQ Protocol Draft for TP-201 (`OQ-TP201` rev 0, status Draft, Indonesian, written against `URS-TP201` rev 1) beside the frozen corpus release 0.1.1, which it refers to by version and manifest SHA-256 and never changes. It is not in TP-201's document list. World data: `world/tp201-oq-draft.yaml`, whose placements are a seeded draw (seed 203) over the TP-201 answer key's values, reproduced by the tests. `uv run python -m traceq_dataset.review_package world/tp201-oq-draft.yaml [--check] [--release dist]` renders the draft, derives `answer_key/TP-201-OQ-draft/` (`defects`, `clean_traps`, `injection_probes`, `test_steps`), writes the release manifest `recordings/TP-201-OQ-draft-0.1.0/manifest.json` (committed, so CI needs no download), validates the key against the draft and the corpus manifest, and with `--release` writes the release folder `dist/TP-201-OQ-draft/`. Pack it as its own release asset with `uv run python scripts/pack_release.py dist TP-201-OQ-draft-0.1.0.tar.gz TP-201-OQ-draft`; its version line is its own, from 0.1.0. Released as a pre-release: fetch it with `gh release download tp201-oq-draft-v0.1.0 --repo gedeyandi123/traceq --pattern 'TP-201-OQ-draft-0.1.0.tar.gz*'`, check it with `sha256sum -c TP-201-OQ-draft-0.1.0.tar.gz.sha256`, extract it, and pass `TP-201-OQ-draft/` to `traceq run --review-package` (below).

Eval: `uv run python -m traceq_eval world/tp201.yaml submission.json [--out report]` scores a recorded system output against the answer key and writes `report.json` and `report.md`; it exits 1 when a gate fails. `--baseline baselines/TP-201.json` adds the ratchet against the accepted baseline and `--write-baseline` writes a candidate (design section 9, "Gates", "Running" and "Scorer"). A submission that answers a Review Package is scored with `--package world/tp201-oq-draft.yaml`: gates over the whole submission and the package's own section, labelled "dev only" (design section 11), ratcheted only against `baselines/TP-201-OQ-draft.json`.

Promote a live run: `uv run python -m traceq_eval promote runs/<run id> --recordings recordings/haiku-rN [--baseline]`, after `traceq run --live --recordings recordings/haiku-rN` (a top-up run, which sent only the calls missing from a renamed earlier folder, works the same). It replays the run from the recordings, refuses (exit 2, nothing written) unless the replay sends nothing and reproduces the live calls, tokens, cost and submission, then writes `report-<tag>.json` (with the live run id) and `run-<tag>.json` into the folder, `baselines/<tag>.json` only when the gates pass, and prints the Equipment's column for the `recordings/README.md` tables (k/n, cost, tokens). It edits no README and leaves no `report/` folder.

Run: `uv run traceq run dist/t0-2026-06-01 [--equipment TP-201] [--out runs] [--recordings recordings]` writes `runs/<run id>/submission.json`, `matrix.json` (Coverage class, reason and cited Evidence per requirement), `drafts.json` (drafted IQ/OQ Test Steps as AI Findings pending review; an Acceptance Criterion only when copied from a verified citation, otherwise empty and flagged "to be set by a human"), `run.json` (settings, model, prompt hashes, tokens, cost in USD, the claims the citation check dropped, and the wall-clock duration with the time spent waiting for live calls apart, 0 for a replay) and `completeness.json` (the URS completeness check, no LLM: printed requirement numbers that did not become a kept requirement, "not applicable" for a URS whose requirements carry no printed number, and URS text no kept requirement quotes; a kept requirement's value quotes count as quoted text). The number check learns the shape of a number from the ids the model returned as printed, so it separates only numbers that look unlike other text: a URS numbered 1, 2, 3 or 4.1 makes every such number on its pages a candidate, and the list over-reports. Test Steps are drafted for requirements the vendor did not cover; `--no-vendor-reuse` drafts one for every requirement ("could be saved by reuse"), but eval runs keep the default, which scorer criterion 1 assumes. Born-digital PDFs are read with Docling on the CPU (its models download from Hugging Face on first use), spreadsheets with openpyxl, and scans with the local OCR model PP-OCRv6 small via RapidOCR 3.10.0, an optional dependency (`uv sync --extra ocr`). Ingest output is cached in `<recordings>/ingest` by document hash and reader version, so a replay with a filled cache runs neither Docling nor the OCR model; `run.json` logs seconds per page and peak RAM per document read. It replays recorded LLM calls and sends nothing; `--live` sends unrecorded calls to Claude through the Batch API (`ANTHROPIC_API_KEY`) and records them, refusing before sending when the estimate passes `--max-usd` (default 1). A Review Package run, `traceq run dist/t0-2026-06-01 --equipment TP-201 --recordings recordings/haiku-r10 --review-package TP-201-OQ-draft --package-recordings recordings/<package run>`, runs the Equipment Pre-review unchanged with every call replayed from `--recordings`, which it reads and never writes, and never sends an Equipment call, also with `--live`: a missing Equipment recording fails the run before anything is sent. The package's own calls and ingest go to `--package-recordings`. The package must refer to the corpus release given (manifest SHA-256) and to the Equipment. The run then reads the package's Protocol Draft, one call per page with the draft prompt (`protocol_draft`, whose hash enters the prompt set only in such a run): its Test Steps (id, requirement ids, the AC as printed with a quote) and its traceability rows, each kept only when its quote passes the citation check. Limits are parsed by code from the print, the AC from the draft and the URS limit from the verified quote of the requirement's URS citation (`traceq.review.printed`; a number that reads two ways or a form it does not know leaves the row "not compared"). The run folder gains `protocol_draft.json` (each Test Step with its AC as read, the URS limit of each requirement the draft's table traces it to, both with citations, and why it was not compared); `submission.json` names the package and carries the draft's Test Step rows; `run.json` names the package, its version, its corpus release and the Equipment recordings replayed, and counts the draft's calls, tokens, cost and Test Steps not compared (the run's totals include them). In a release folder the manifest's document path `<package>/<file>` is read as `<file>` inside the package folder. Module boundaries are checked by import-linter (`uv run lint-imports`, also run by the tests).

Serve: `uv run traceq serve [--runs runs] [--corpus dist/t0-2026-06-01]` starts the read-only API over the run folders (GET only; it reads only `run.json`, `matrix.json`, `findings.json`, `completeness.json` and, for a Review Package run, `protocol_draft.json` of a run, and the documents the run read; a scorer report or anything else in the folder is never opened). With `--issuer URL --database URL` (a demo issuer from `traceq demo-issuer`, a database URL connecting as `traceq_app`; `--audience`, `--role-claim`) it also opens the database routes, each behind a bearer token of that issuer: `POST /runs/{run_id}/import` (deciding role; one transaction; importing again changes nothing), `GET /runs/{run_id}/proposals`, `POST /runs/{run_id}/proposals/{proposal_id}/decisions` (deciding role; one Proposal Decision with its Audit Trail entry; a Reason for Change for a rejection, a changed class or a replaced decision), `GET /runs/{run_id}/decision-counts` (per kind of Proposal, by decision state) and `GET /runs/{run_id}/protocol-draft` (a Review Package run: the draft's Test Steps, traceability rows and findings, each finding with its Proposal once imported). Without both every database route answers 401, and it refuses to start with only one of the two. The UI in `web/` (Next.js, Bahasa Indonesia via next-intl) shows the traceability matrix with Evidence links that open the cited page: `cd web && npm ci && npm run dev`, with the API at `TRACEQ_API_URL` (default `http://127.0.0.1:8000`; the `/api` rewrite reads it at build time). The TypeScript client is generated from the OpenAPI schema: after an API change run `npm run openapi && npm run generate` in `web/` and commit both files (`tests/test_api.py` and CI fail on a stale schema or client). Web checks: `npm run typecheck`, `npm test`.

Eval screen: scores come from the harness, never from the system's API. Score a run into its folder (`uv run python -m traceq_eval world/tp201.yaml runs/<run id>/submission.json --out runs/<run id>`), then `uv run python -m traceq_eval.screen serve [--runs runs] [--port 8001]` serves, per scored run, the report's headline rates with k/n and its split (dev TP-201, held-out otherwise; both written by the scorer, the screen counts nothing), the gate verdict and the run's cost; never report items or baselines. The UI reads it at `TRACEQ_EVAL_URL` (default `http://127.0.0.1:8001`); its client is generated from `web/eval-openapi.json` by the same `npm run openapi && npm run generate` (`tests/test_eval_screen.py` fails on a stale schema).

Database: Postgres 17 holds what humans write (spec #105). `docker compose up -d postgres` starts it on `127.0.0.1:5432` (superuser `postgres`, password `postgres`; local demo server only). Two roles, created idempotently by `src/traceq/db/roles.sql` when the volume is first initialised and by the test fixture, never dropped: `traceq_owner` owns the schema and runs the Alembic migrations (`traceq.db.upgrade`), `traceq_app` is what the application connects as. The Audit Trail is append-only: the application role has no UPDATE, DELETE or TRUNCATE grant on it, and triggers refuse those statements to every role. **Limit:** there is no hash chain yet (ADR 0007, phase 3), so the trail resists the application, not a database administrator: the owner role or a superuser can drop the triggers and rewrite it without a trace. The database tests create a uniquely named database per session and drop it at the end; they connect through `TRACEQ_TEST_ADMIN_URL` (default `postgresql+psycopg://postgres:postgres@127.0.0.1:5432/postgres`), are skipped with the reason when Postgres is not reachable, and fail instead in CI (`CI` set), where Postgres runs as a service container.

Sign-in screen (web, `/signin`): the Next.js server lists the demo personas from the issuer at `TRACEQ_ISSUER_URL` (default `http://127.0.0.1:9000`), asks it for the chosen persona's token, keeps it in an httpOnly cookie (never in client-side JavaScript) and sends it to the API as a bearer token; the UI says "identitas demo" wherever it shows who is signed in, and signing out clears the cookie. `TRACEQ_ROLE_CLAIM` (default `roles`, a dotted path for a nested claim; the same setting as the API's `--role-claim`) names the claim the web reads to show whether the persona may decide; display only, the API checks the role on every call.

Identity (spec #105, ADR 0005): `traceq.identity` verifies standard OIDC bearer tokens: signature through the issuer's JWKS (found through its discovery document), issuer, audience and expiry. The claim holding the roles is a setting (`roles` by default, a dotted path such as `realm_access.roles` for Keycloak). One role decides in this slice, `qualification-decider`: it may import a run and record Proposal Decisions; anyone else signed in may only read. `uv run traceq demo-issuer [--port 9000] [--audience traceq]` starts the demo issuer, a separate application on `http://127.0.0.1:PORT` only: a discovery document, a JWKS (a new key per start) and, without a password, a token for any of three seeded personas with fictional names (`GET /demo/personas`, `POST /demo/token {"username": ...}`), two of them with the deciding role. These are demo identities, not access control; Keycloak replaces the issuer by changing the issuer URL.

Demo (spec #105): `uv run python scripts/demo.py CORPUS_DIR --recordings RECORDINGS_DIR [--no-compose]` brings the demo to a known state and, run again, resets it. Prerequisites: Docker (Compose), `uv sync`, Node for the UI, `CORPUS_DIR`, an extracted corpus release (the release asset, for example 0.1.0; the release is read from its `manifest.json`), and `RECORDINGS_DIR`, the recordings set made on that release (`recordings/haiku-r10` for 0.1.1, `recordings/haiku-r7` for 0.1.0; `recordings/haiku-r8`, also on 0.1.1, needs a checkout before r9, a975cae). Before anything changes, the command checks that every TP-201 document has the SHA-256 of the manifest and an ingest entry in the recordings, and refuses with the reason (the database stays as it is) when a file is missing or the pair does not match. In order it: starts Postgres (`docker compose up -d --wait postgres`; `--no-compose` when one already runs), creates the roles if missing, drops and recreates the `traceq` database as `traceq_owner`, applies the migrations, replays the TP-201 recordings of `RECORDINGS_DIR` (`scripts/demo.py` fixes TP-201 as a constant: the held-out Equipment cannot be chosen) into `runs-demo/` (no LLM call; the held-out Equipment is never loaded), starts the demo issuer (`127.0.0.1:9000`) and the API (`127.0.0.1:8000`) as local processes, and imports the run through the API as the persona `ayu`. Afterwards three processes run: Postgres (Docker), the issuer and the API; the command stays in the foreground and Ctrl-C stops the issuer and the API (Postgres stays up). Start the web UI: `cd web && npm ci` once, then `npm run build && npm start` for a demo (or `npm run dev` while developing). Running it again drops the database, so decisions and the Audit Trail start from zero (the limit above: a database drop is exactly what the trail does not resist); stop the earlier run first, because its ports are taken. Demo identities, all fictional and without a password: `ayu` and `bima` hold the deciding role, `citra` may only read; the UI labels them "identitas demo". Last rehearsed on 2026-11-17 (UTC) with corpus release 0.1.1, `recordings/haiku-r10` and the production web UI on Windows, all 17 cases passing; the steps, test cases, known errors of the r10 run and recovery after a reset are in [`docs/demo-runbook.md`](docs/demo-runbook.md) (Indonesian, for the practitioner session).

Hooks: ruff, gitleaks, and a denylist check. The denylist blocks real equipment vendor names (`denylist/public.txt`) and private terms kept in a gitignored `.denylist.local` file (CI reads them from the `DENYLIST` secret).

Workflow: short branches (`feat/`, `fix/`, `docs/`, `chore/`, `test/`, `refactor/`), [Conventional Commits](https://www.conventionalcommits.org/), squash-merge via PR. A spec is built on an integration branch that reaches `main` in one PR ([`CLAUDE.md`](CLAUDE.md)).
