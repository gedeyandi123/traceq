# The Protocol in TraceQ is assembled from decided Proposals and frozen when submitted

Decided 19 November 2026 for step 5a of ADR 0010, before its spec, after a fresh-context doubt review.

Execution (step 5b) is judged by code (ADR 0002), so it needs a Protocol whose Test Steps and Acceptance Criteria are structured data. A site's Protocol Draft is a document that Pre-review reads but cannot execute, so the Protocol is assembled inside TraceQ: one row per requirement of one run, for one Equipment, IQ and OQ combined (the drafted Test Steps are drafted for "IQ/OQ" and carry no Stage, and ADR 0010 does not extend them).

**Rows.** A requirement whose human-decided Coverage is `covered_by_vendor` is a Vendor Reference, and its drafted Test Step, if any, needs no decision; accepting it anyway makes the row a Test Step (tested again on site). Every other requirement needs exactly one Test Step: a drafted one accepted or edited, or one a human wrote because none was accepted. A written Test Step keeps every earlier version (who, when, old and new content) without a Reason for Change while the Protocol is a Draft, since it is not yet a GMP record (ADR 0009); a draft cannot be accepted while a written Test Step exists for its requirement.

**Submission** needs: every Coverage class decided by a human; every drafted Test Step of a non-vendor row decided; every non-vendor row with its one Test Step; every Acceptance Criterion in a shape code can judge (range, number, one of, present), free text refused; and every printed requirement number the run missed (the URS completeness check) answered by a human as "not a requirement" or "a requirement this Protocol does not test", each with a written justification. URS text no requirement quotes is shown, not answered. A row with no Test Step blocks; a missed requirement may be excluded with a justification, because a row always has a way to get a Test Step and a missed requirement has none.

**Freezing and approval.** Proposal Decisions are only added and are shared across runs, so a Protocol that read them live could change under its Approver. On submission the Protocol stores a copy of every row, the answers on missed requirements and the unquoted URS text, and the hash of that copy. Protocol Approval is a recorded status bound to that hash, labelled not an Electronic Signature (ADR 0007 phase 2; signed from step 8, see ADR 0007 amendment of 26 November 2026); later decisions only affect a later Protocol. The Approver holds an approving role, is not the Preparer, and recorded none of what the copy rests on: the decisions in force (Coverage decisions included), the answers on missed requirements, and the written Test Steps.

**Statuses:** Draft, Submitted, Approved, and Withdrawn (a Draft given up with a reason, so a newer run can get a Protocol). An Approver may return a Submitted Protocol to Draft with a reason; the returned copy stays as history. One Protocol per Equipment may be open at a time, and none may be started once one is approved: a new version is step 6.

## Amended 26 November 2026: the Protocol may start from the site's reviewed Protocol Draft

Decided by the owner on 26 November 2026 (see ADR 0010 of the same date). Wording of "one row uses one source", of the submission rule for findings and of the wider separation of duties settled the same day, in answer to the owner's choices "Sumber per baris (Recommended)", "Blokir + alasan (Recommended)" and "Sedang (Recommended)". Until now the Protocol was assembled from TraceQ's own drafted Test Steps, so the draft that Pre-review reviewed was never the document that Execution ran. The Considered Option "Execute the site's Protocol Draft" is reversed in part: its objection (no human decides the rows) is met, because every row below is decided by a human.

- **Source.** For a run with a Review Package, a Protocol may start from the site's Protocol Draft instead: each Test Step the system read from the draft with a verified citation becomes a candidate row; a draft Test Step the citation check dropped is listed on the Protocol for the Preparer, not only in run metadata (ADR 0009); one that maps to no requirement, or to several, is left to the spec. The Test Step and its Acceptance Criterion are Proposals, as before: a human accepts or edits each, and an Acceptance Criterion read from a document needs a Proposal Decision before approval (ADR 0010).
- **Submission.** The rules of Submission above apply unchanged to a draft-sourced Protocol, with one point settled: a `covered_by_vendor` row that has a draft step needs no decision on it, as above, and if the step is accepted the rule below applies. For every other draft-sourced row a human decides both the Test Step and its Acceptance Criterion (accept or edit); a row left unread, or a criterion only displayed, blocks submission. One row uses one source: a requirement the draft covers takes its Test Step from the draft, any other (the draft is OQ only, so IQ requirements) from the system's own drafted Test Steps or a written one, never both, so a row never carries two Test Steps. The source of each row is recorded in the frozen copy.
- **Binding to content.** A Proposal Decision on a draft row binds to the Test Step's identity and to the content hash of the Test Step, the requirement it maps to and its Acceptance Criterion. If a later revision changes any of them, the row is undecided again. A Draft Protocol never re-syncs after Submission, and a return to Draft keeps the revision it was read from. Edits by a human are typed content and need no second decision.
- **Frozen copy.** The copy also records the draft's document version, revision and hash and the run it was read from, and the carried-over findings shown at approval are part of the copy and its hash. The Approver is shown when the source revision is no longer the latest. Approval covers TraceQ's copy, not the site's document.
- **Findings carry over.** An accepted finding about a draft row ("this is a real defect and will be fixed") is shown on that row until the Test Step is edited or a later revision of the draft resolves it. A later revision resolves it only when the round-over-round diff says so, never by a person marking it silently, and only for a Protocol started from that later revision: a Protocol stays pinned to the revision it was read from. The carry-over reads Proposal Decisions only for display; Eval runs never read them. At submission a finding about a row that is still undecided blocks; an accepted finding on a row whose Test Step and Acceptance Criterion are unchanged needs a written reason, which the frozen copy records and the Approver is shown. The Approver is also not the person who decided a Pre-review finding or mapped a draft step to a requirement on that run.
- **Stage.** The draft carries no Stage; a human sets IQ or OQ per Test Step, as the consequence of this ADR already anticipated.
- **Open question and marking.** Whether a plant executes the draft it reviewed is a question for the practitioner (#245). Until it is answered, the UI and the demo runbook mark the draft-sourced path as awaiting it. If the answer is no, this path is removed, not patched.

## Amended 27 November 2026: a Protocol pinned to an older revision is refused, not only shown

Decided by the owner on 27 November 2026 (ticket #393, spec #375), in answer to the question what happens when a newer revision of the Protocol Draft arrives while a Protocol started from an older one is open: "Tolak approve bila revisi lama (Disarankan)". It replaces "The Approver is shown when the source revision is no longer the latest" in the frozen copy rule above, and gives the word "unchanged" in the findings rule a meaning.

- **Refused at signing.** Submitting and approving a draft-sourced Protocol are refused (409, with the pinned and the latest revision named in the message) while the revision it is pinned to is older than the latest registered revision of that draft document, whatever revision the caller says it read. The Protocol never re-syncs: it is withdrawn (from Submitted, first returned to Draft, which stays allowed and keeps its pin) and a new Protocol is started from the latest revision. The existing check that the caller read the latest revision stays, so a caller who read an older page is still sent to reload.
- **Unchanged means the same content.** The accepted-finding rule above applies to a row whose Test Step and Acceptance Criterion equal the draft's (description, method, instrument and criterion, blanks aside). Saving a written Test Step with the draft's own content is not a change and does not clear the need for a written reason; only a real difference does, and saving the draft's content back asks for the reason again.

## Considered Options

- **Execute the site's Protocol Draft (reversed in part, see Amended 26 November 2026):** its Test Steps and Acceptance Criteria are read with verified citations, but no human decides them, and the Review Package holds only an OQ draft.
- **Read decisions live until approval:** simpler, but an Approver could approve content other than what they read.
- **Separate IQ and OQ Protocols:** the drafts carry no Stage, so a requirement whose draft belongs to the other Stage would block submission with no honest way out.
- **Block submission on any missed requirement number:** a replayed run misses the same numbers again, and a URS numbered `4.1` over-reports by design, so submission could never happen.
- **Approver only differs from the Preparer:** allows deciding rows and then approving them.

## Consequences

- Known limits, stated in the product: one Test Step per requirement; no printed or exported Protocol (not in the order of ADR 0010; on the practitioner agenda, #245); no new version after approval until step 6.
- The document Pre-review reviewed is not the one executed unless the Protocol is started from the draft (amendment of 26 November 2026).
- Execution and the Qualification Report (steps 5b and 7) are per Stage, so a combined IQ/OQ Protocol is debt for step 7; a Stage set by a human per Test Step is the likely way out.
- Status changes are appended events, since the tables refuse UPDATE. A demo rehearsal starts again from a reset database, because an approved Protocol blocks a new one.
- The demo issuer gets a fourth fictional persona holding only the approving role.
- Eval runs never read Protocols, decisions or written Test Steps.
